# MQ 结论分层与模型目录跨批次对比

日期：2026-11-04
范围：`mq/mq.py` v0.1.0 → v0.2.0、`mq/hub/app.py`、`scripts/hub_gate.py`

## 起因

一次真实测试暴露了 v0.1.0 的三个设计问题。不是某个函数写错，而是**结论的表达方式掩盖了证据**。

同一个端点在 37 分钟内被测了两次，两次的 `GET /v1/models` 结果如下：

| 测试时间（UTC） | 模型数 | 家族构成 |
|---|---:|---|
| 2026-11-05T01:29:34Z | 11 | `claude` × 11 |
| 2026-11-05T02:06:27Z | 9 | `gpt` × 9 |

两次的模型集合**交集为空**：11 个 `claude-*` 全部消失，换成 9 个 `gpt-*`，零重叠。

而这正是本项目的核心检测目标。但 v0.1.0 给出的结论是：

```
结论: 证据不足 —— 基础 Messages 调用失败，无法取得证据
```

两份报告的模型列表都被放在文末 `<details>` 折叠块里。也就是说：**工具抓到了它要抓的东西，然后用一个错误分类把它埋掉了。**

## 三个设计缺陷

### 一、结论不分层

v0.1.0 只有四个结论，其中 `evidence_insufficient` 同时覆盖了至少四种完全不同的故障：

| 实际发生 | 用户该做什么 | v0.1.0 结论 |
|---|---|---|
| 声明模型不在目录（404 model_not_found） | 改 PR 里的模型声明 | 证据不足 |
| 上游 502 / 503 | 等端点恢复后重测 | 证据不足 |
| Key 无效（401） | 换 Key | 证据不足 |
| 真的协议不兼容 | 不要用这个端点 | 证据不足 |

四种情况，一个标签。用户读完仍然不知道该做什么。

### 二、模型目录被当作证据而非结论

`/v1/models` 是整份报告里信息密度最高的一项：它直接回答「这个端点声称提供什么」。v0.1.0 把它当成一条普通探针，和「system 透传」平级，并且只把模型列表塞进 `<details>`。

更严重的是声明模型不匹配时的处理：旧逻辑会静默换成 `claude-haiku-4-5-20251001` 或目录第一个模型继续测，最后给出一个混合结论——用户看到的是「测试完成」，实际上是「测的不是你声明的那个模型」。

### 三、没有跨批次对比

每次测试都是孤立快照。**换上游、混轮、临时切换账号池，只有把两次结果放在一起才看得见。** 一个做质量监测的工具，缺了时间维度就等于没有监测。

v0.1.0 的报告目录里其实存着历史，但代码从来不读。

## v0.2.0 的改动

### 结论按「下一步该做什么」分层

| 结论 | 触发条件 | 门禁 |
|---|---|:---:|
| `basic_passed` | 协议与行为特征全部通过，且声明模型存在 | ✅ |
| `endpoint_unreachable` | 网络/TLS/超时，或基础调用 5xx | ❌ |
| `auth_rejected` | 基础调用 401/403 | ❌ |
| `model_not_found` | 声明模型不在 `/v1/models` | ❌ |
| `protocol_incompatible` | Messages 路径 404 或响应结构不符规范 | ❌ |
| `behavior_anomaly` | 核心协议项（流式 / system / tools）失败 | ❌ |
| `identity_suspect` | tokenizer 不一致、官方对照不符、目录家族翻转 | ❌ |

判定顺序即优先级：先回答「通了吗」，再回答「声明的模型存在吗」，最后才谈协议细节和身份证据。只有 `basic_passed` 会让 Hub 判为 `verified=true`。

### 模型目录升为第一组结论

报告结构改为五组，顺序即阅读优先级：

```
一、模型目录      ← 声明模型存在性 / 家族构成 / 与上次对比
二、端点可用性    ← 基础调用 + HTTP 状态分级
三、协议兼容性    ← 流式 / system / tools / thinking
四、身份证据      ← count_tokens 指纹 / 计数一致性 / 官方对照 / 自述
五、稳定性与性能
```

声明模型不存在时，不再静默替换：报告顶部直接标注「模型替换 ⚠️」，结论固定为 `model_not_found`，并列出相近候选（例如声明 `gpt-6.1-luna` 而目录里只有 `gpt-6-luna`），帮助判断是拼写问题还是真没有。

### 新增跨批次目录对比

Hub 在每次运行前查找该 PR 上一次的 `report.json`，通过 `--previous-report` 传给引擎。对比项：

- 新增 / 消失的模型 id
- **家族构成是否翻转**（例如 `claude×11 → gpt×9`）

家族翻转判为 `FAIL` 并直接进入 `identity_suspect`。集合变动但家族不变判为 `WARN`。

### 模型自述降级为零证据探针

「问模型你是谁」这条探针在新版本里只记录、不参与判定。理由很直接：模型会照着 system prompt 回答，中转站可以随手指示它自称 Claude。把它当证据，等于把决定权交给被检测方。

v0.1.0 里还有一条更危险的隐含逻辑：声明 `gpt-x` 而自称 `gpt-x` 视为「一致、不扣分」。对一个专门收录 Claude 中转站的目录，这个判定方向是错的。

### 新增 `count_tokens` 指纹

`POST /v1/messages/count_tokens` 只返回 token 数，不产生输出，结果完全由「分词器 + 模型」决定。它比「重复请求计数是否恒定」更强：恒定只能证明同一次请求内自洽，`count_tokens` 可以拿固定文本和官方端点逐字节比对。

端点不支持该路径时记为 INFO（可选能力），不扣分。

## 证据边界（不变）

- 目录家族检查只能证明「它声称提供什么」。同一端点可能出现多家族混排，也可能因负载均衡对不同请求返回不同目录——**观测到的变化不等于主观换壳，需要连续多次采样才能定性**。
- `basic_passed` 仍不代表模型为真、不代表安全、不代表稳定。
- 任何短时黑盒测试都无法证明服务商不留存、不转卖请求。

## 复现

```bash
# 首次
python3 mq/mq.py --base-url https://api.example.com --key sk-xxx --json run1.json

# 之后每次带上上一次的 report.json
python3 mq/mq.py --base-url https://api.example.com --key sk-xxx \
  --previous-report run1.json --json run2.json
```

Hub 侧无需手工传参，会自动使用该 PR 最近一次的 `report.json`。
